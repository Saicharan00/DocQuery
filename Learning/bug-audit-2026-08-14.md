# Whole-codebase bug audit — 2026-08-14

Four agents, one per quarter of ~7,200 lines, run against branch
`worktree-day10b-error-sweep` (i.e. **after** the Day 10b fixes). 30 findings.

Each was told the codebase is heavily commented with deliberate trade-offs, and that
a thing a comment justifies should only be reported if the justification is *wrong*
or has an unhandled edge. They were also given the Day 10b fix list so they would not
re-report it — and asked explicitly to scrutinise the new code rather than trust it.

**VERIFIED** = I re-read the code and confirmed it personally.
**CONFIRMED** = the agent traced it and I have no reason to doubt it.
**PLAUSIBLE** = depends on library behaviour nobody verified.

## Tier 1 — data loss, outage, or money

### 1. A brief Clerk outage takes the whole API down, unnecessarily — VERIFIED
`apps/api/app/deps.py:80-107`

Once the JWKS cache is older than `JWKS_TTL_SECONDS`, `needs_fetch` is true, so the
early return is skipped **even when the token's `kid` is already cached**. Inside the
lock both checks fail (age > TTL, age > 30s), leaving only a network refresh. If
Clerk's JWKS endpoint blips, every authenticated request 503s while the process holds
the exact key needed. The lock is held *across* a 10s-timeout HTTP call, so N
concurrent requests queue at 10s each and the pile-up outlives the outage.

RS256 signing keys live for months. The module's own comment says Clerk rotates them
rarely — which is the argument for serving the stale key. The code does the opposite.

**Fix:** on refresh failure, fall back to the cached key if the `kid` is present.

### 2. Answers routinely vanish on reload — VERIFIED
`apps/api/app/routers/chat.py:487`, `:266`

`_save_exchange` and `_retitle` run *after* the stream, using the request-scoped
Supabase client that carries the caller's Clerk JWT verbatim. `/chat` never takes the
`TokenExpiry` dependency — it does not import it — yet `ANSWER_TIMEOUT = 60` lets the
stream run a full minute past validation. Clerk hands the browser a *cached* token, so
starting with ~20s of life is the normal case, not the edge.

Result: every token reaches the browser, `done` fires, the UI shows a complete cited
answer — then the insert 401s and `_save_exchange` swallows it. On reload the answer
is gone. For a new conversation the `conversations` row survives (inserted earlier,
while the token was valid), so the sidebar shows a conversation with a placeholder
title and zero messages.

This was on the "known, deliberate, awaiting a decision" list. The audit's contribution
is *why it fires routinely rather than exceptionally* — and that `documents.py:369`
already solves exactly this with `TokenExpiry`, a fix pattern sitting in the same repo.

**Fix:** take `TokenExpiry` in `/chat`; refuse to start if the remaining budget is
under the answer timeout, or re-validate before the write.

### 3. Concurrent ingest steps double-bill and corrupt a healthy document — VERIFIED
`apps/api/app/routers/documents.py:440-455`, `:540`, `:583-611`
`apps/web/src/app/dashboard/page.tsx:66-67`, `:151-159`

**Found independently by two agents from opposite ends** — the strongest signal in the
audit.

`ingest_step` has a `ready` guard but no lock and no in-flight guard. Two steps read
the same `resume_from`, **both pay Cohere for the identical batch**, one insert wins,
the other violates `chunks_document_chunk_idx` and lands in the generic `except` →
`_set_status('failed')` with *"Something went wrong while reading this file"* about a
file that is fine. Worse ordering: if the winner sets `ready` first, the loser
**overwrites `ready` with `failed` on a fully-ingested document**.

Two independent triggers:
- **Two tabs**, or a reload mid-step — `running` is a per-tab `useRef`.
- **Navigate away and back.** The `while (!done)` loop is a plain async function with
  no `AbortController` and no cleanup. Leaving `/dashboard` does not stop it; coming
  back mounts a fresh page with an empty `running` set and starts a *second* loop on
  the same document. The remount also clears `abandonedIds`, so a document you had
  given up on loses its Retry button and gets auto-driven again.

**Fix:** a status/lease guard server-side (only one step in flight per document), and
an `AbortController` + unmount cleanup client-side. The server guard is the load-bearing
half — it closes both triggers at once.

### 4. The history fetch can hijack a live answer — VERIFIED
`apps/web/src/components/chat-view.tsx:381-394`, with `:429-438`

`updateLast` rewrites by **index** (`current[current.length - 1]`), while the history
effect does a wholesale `setMessages(rows.map(...))` replace. The composer is not gated
on `isLoadingHistory` — Send is disabled only on `isStreaming || empty input`.

Open a saved conversation on a cold backend, type before "Loading conversation…"
clears: your question and the streaming reply are replaced by the old messages, and
every subsequent token appends onto the last *historical* row — quite possibly one of
your own user bubbles, so the model's reply visibly grows inside a blue user bubble.
`runId` and `sources` land on that wrong row, so the feedback thumbs beneath it report
against a different answer.

The window is wide on `/chat/[id]` because the effect runs twice: once throwing
`AuthNotReadyError` while Clerk loads, then again for real. Everything is interactive
throughout.

**Fix:** gate the composer on `isLoadingHistory`, and/or make the history load merge
rather than replace when messages already exist.

## Tier 2 — user-visible wrong behaviour

### 5. A real Clerk key rotation reads as "your session has expired" — VERIFIED
`apps/api/app/deps.py:92-94` + `apps/web/src/lib/api.ts:96-104`

The 30s anti-hammer throttle rejects an unknown `kid` with a **401**, not a 503. The
`fetchWithToken` retry (added in Day 10b) treats any 401 as a stale token and retries
within milliseconds with `skipCache` — same window, same unrecognised `kid` → second
401 → `SessionExpiredError`. A healthy user is told to sign in again, and refreshing
does not help because the new token carries the same new key.

The throttle is right for garbage tokens; it just cannot distinguish a legitimate
rotation, and the automatic retry burns the whole window instantly.

**Fix:** return 503 (not 401) for an unknown `kid` inside the throttle window, or
exempt a `kid` never seen before from the throttle.

### 6. The daily message cap is TOCTOU and under-counts spend — CONFIRMED
`apps/api/app/routers/chat.py:56-113` vs `:487`; `005_chat.sql:104`

Two separate defects:
- The cap counts `messages` rows at the *start*, but the row is inserted at the *end*
  of the stream. Submit N+10 tabs simultaneously and all pass. Any path that fails to
  write (finding 2, empty answer, disconnect) leaves the counter unchanged after a
  paid call — so a user whose answers routinely outlive their token never increments
  at all.
- The `role = 'user'` counting rests on "one user message is exactly one LLM call".
  **Since Day 9b that is false**: `rewrite_query` and `generate_title` are two more
  billed completions. The comment asserting the invariant is what would stop anyone
  noticing.

### 7. The stream reader is never torn down when the generator throws — CONFIRMED
`apps/web/src/lib/api.ts:237-322`

`getReader()` is acquired with no `try/finally`. Two live paths throw out of the
generator — the 20s stall timer and the corrupted-stream error — leaving the reader
locked and the fetch alive. `chat-view`'s `finally` sets `abortRef.current = null`
*without* calling `.abort()`. Per `chat.py:554`, the server generator then stays
suspended and the model stream stays open and billable. The mechanism added to turn an
invisible dead connection into a visible error leaves the connection itself running.

### 8. Deleting a document mid-ingest leaves a stuck error banner — CONFIRMED
`apps/web/src/components/document-list.tsx:151-170` + `dashboard/page.tsx:121-127`

Deleting does not stop the loop driving that document. Its next step 404s → not an
`AuthNotReadyError` → `setDocumentsError("Document not found.")`. Only `retry` or a
successful `refreshDocuments` clears it, and the user has no reason to trigger either.
Highly reproducible: a step is in flight most of the time.

### 9. Failed streams leave empty conversations in the sidebar forever — CONFIRMED
`apps/api/app/routers/chat.py:424`

The `conversations` row is inserted before the stream opens. Any failure after that
leaves a titled conversation with zero messages, never cleaned up, `_retitle` never
runs. The code at `:352-358` explicitly reasons about this hazard for the *embed* call
but leaves the far larger LLM-stream window uncovered.

### 10. Every streamed token force-scrolls to the bottom — CONFIRMED
`apps/web/src/components/chat-view.tsx:353-355`

The effect depends on `messages`, and `updateLast` makes a new array per token, so
`scrollIntoView` fires hundreds of times per answer with no "is the user near the
bottom?" check. Scrolling up to re-read anything mid-answer is impossible.

### 11. "No session at all" is reported as an error everyone ignores — CONFIRMED
`apps/web/src/lib/api.ts:83-89`

By line 83 Clerk *is* loaded, so a null token means there is no session — which does
not resolve itself. It is thrown as `AuthNotReadyError` ("ignore me, I fix myself").
Twenty lines later the identical null is classified `SessionExpiredError`; the file
contradicts itself. `refreshDocuments`, `document-list` and `upload-zone` all swallow
it, and **the dashboard has no `AUTH_WAIT_MS` timer**, so it sits empty indefinitely.

### 12. The sidebar's new 10s auth ceiling can never fire — CONFIRMED (my own Day 10b code)
`apps/web/src/components/conversation-sidebar.tsx:95-117`

`pathname` is in the dependency array as the refetch trigger, so the countdown restarts
on every URL change — including `ChatView`'s `history.replaceState`. In the exact
scenario the timer was written for, clicking around resets it forever.

The `chat-view.tsx` timer was checked and found correct, as was the `abandonedIds`
ref/state mirroring.

## Tier 3 — latent, conditional, or silent

### 13. An `IndexError` that wedges a document permanently — VERIFIED
`apps/api/app/routers/documents.py:578`

`chunks[written - 1]`, where `written` starts at the resume point but `total` is
recomputed every step. If a recomputation ever yields fewer chunks than are stored →
IndexError → generic handler → `_set_status('failed')` *immediately after having just
set `ready`* → and every retry recomputes identically. No way out but delete and
re-upload. Trigger is a config/library change; `MAX_IMAGES_PER_DOCUMENT` has already
moved once (50→75). One `min()` closes it.

### 14. Tracing silently disables itself with no log line — CONFIRMED
`apps/api/app/services/tracing.py:65-74`

The `else` branch fires when `langsmith_tracing` is true but the API key is empty,
writes `LANGSMITH_TRACING=false`, and says nothing. This module exists *because* a
silent tracing-off bug (the `"True"` vs `"true"` casing issue) cost real debugging
time — and it reintroduces the same class of failure for the likeliest
misconfiguration. One `logger.warning` closes it.

### 15. `_session_id()` caches a failure for the life of the process — CONFIRMED
`apps/api/app/services/tracing.py:183-197`

`@lru_cache(maxsize=1)` memoizes the `None` returned on exception as happily as a real
id. One transient network blip on the first `record_feedback` after a deploy means
every piece of feedback for that container's whole life is filed without a
`session_id`. Restart is the only recovery and nothing surfaces it.

### 16. Transient provider errors are blamed on the user's file — CONFIRMED
`apps/api/app/routers/documents.py:484-495`, `:601-607`

The rate-limit carve-out covers exactly one exception type. A Cohere 5xx, a read
timeout, an `httpx.ConnectError`, or a Storage blip all mark the document `failed`
with *"Something went wrong while reading this file… re-upload it"* — and re-uploading
discards the resume point and re-embeds everything at full cost, where simply calling
the step again would have resumed free.

### 17. Every chart in a slide deck can be silently deleted — CONFIRMED
`apps/api/app/services/ingestion.py:442-452`

The repeat filter drops boxes appearing in the same position on `max(3, pages × 0.5)`
pages unless they cover ≥50% of the page. A slide deck exported to PDF puts one chart
per slide in the same placeholder at ~30-45% of the page — so on a 10-slide deck all
ten charts are discarded. No `on_reject` is passed, so nothing is logged and nothing
reaches the user; `images_total` just reports 0 and ingestion "succeeds".

### 18. `ChunkImage` never aborts, and revokes a URL still held in state — CONFIRMED / PLAUSIBLE
`apps/web/src/components/chat-view.tsx:48-77`

No `AbortController`, so switching conversation leaves every in-flight figure
downloading. On a *dependency change* rather than unmount, cleanup revokes the object
URL while `url` state still holds it, so `<img src={revoked}>` renders broken until the
refetch lands.

### 19. Nothing bounds concurrent ingest steps — CONFIRMED (allocations), threshold untested
`apps/api/app/routers/documents.py:361-371`

Each in-flight step holds the downloaded file (≤10MB), parsed text, up to 75 rendered
JPEGs, and a batch of 96×1536 float vectors (~4.7MB) plus its JSON serialisation —
comfortably 30-50MB. The AnyIO pool defaults to 40 threads and there is no semaphore.
The per-day caps do not limit *concurrency* at all.

### 20. An 8-image batch can exceed Cohere's request ceiling — PLAUSIBLE
`apps/api/app/services/ingestion.py:44-46`, `:77`, `:518-543`

`IMAGE_EMBED_BATCH_SIZE = 8` is justified by "eight crops at roughly 100KB each", but
`MAX_IMAGE_PIXELS = 2_000_000` permits crops 20× larger, and base64 adds a third. Eight
scanned pages ≈ 11-16MB. A size rejection is not `TooManyRequestsError`, so it marks
the document failed — and `_batches` is deterministic, so every retry rebuilds the
identical oversized batch and fails identically.

### 21. Deleting mid-step orphans JPEGs — CONFIRMED
`apps/api/app/routers/documents.py:788-798` vs `:513`

Delete lists image paths, removes objects, deletes the row. An in-flight step uploads
its JPEG *before* inserting the row, so objects uploaded after the `remove()` have no
row pointing at them and are unreachable by any future delete.

### 22. Partial feedback success reported as total failure — CONFIRMED
`apps/api/app/routers/feedback.py:71` + `tracing.py:219-231`

Score and comment are two `create_feedback` calls in one `try`. If the score succeeds
and the comment fails, the endpoint 502s and the user is told nothing was recorded —
but the score is already filed. Retrying double-counts, which is exactly what the
split-submission design exists to prevent.

### 23. `stream_answer`'s documented guarantee does not hold — CONFIRMED
`apps/api/app/services/rag.py:616-630`

The docstring promises it "raises before the first token if the model is unusable".
It contains `yield`, so calling it executes nothing — `api_key_for(model)` runs at the
first `next()`. `/chat` is safe only via a separate pre-flight. The module docstring
says these functions exist standalone precisely so Day 11's eval harness can import
them, so this will mislead that harness.

### 24. `repr(exc)` of an arbitrary exception goes into a possibly-public trace — PLAUSIBLE
`apps/api/app/routers/chat.py:428`

Defended as "HTTPException prints status and detail, and this goes to our dashboard,
not a browser". Two holes: `load_images`, `build_messages` and `to_sources` are
unwrapped, so a raw supabase/httpx repr lands there; and the reasoning 90 lines above
hashes the Clerk id *specifically because* "a trace can be made public for the README".
No path found where a key leaks (supabase-py sends credentials as headers), so this is
request-detail exposure, not secret exposure.

### 25. Unbounded selects can be silently truncated — PLAUSIBLE
`apps/api/app/routers/conversations.py:109-121`, `:78-83`

Neither `list_messages` nor `list_conversations` sets a range. PostgREST enforces
`db.max-rows` (default 1000) and returns a truncated set with a **200**, so the handler
cannot tell a full result from a clipped one.

### 26. A Supabase client per request, never closed — PLAUSIBLE
`apps/api/app/deps.py:212-222`

`create_client` builds GoTrue, Realtime and PostgREST clients per request, each with
its own `httpx.Client`. Nothing closes them. `auto_refresh_token=False` /
`persist_session=False` correctly prevent the worse version; the teardown is missing.

### 27. `azp` is never checked — PLAUSIBLE
`apps/api/app/deps.py:135-142`

`verify_aud: False` is correct (Clerk session tokens carry no `aud`), but the
substitute Clerk documents — validating `azp` against allowed origins — is not done.
The only origin restriction is CORS, which is not an authorization control.

### 28. The token budget is checked only after a paid call — CONFIRMED
`apps/api/app/routers/documents.py:396-399` vs `:475-564`

`budget` is consulted at `:563`, *after* a batch is embedded and written. The download,
parse and full image render run unmetered, and the first Cohere call is made
unconditionally even when the budget is already negative.

### 29 & 30. Lower-value items
- `chat.py` still collapses every mid-stream failure into "The answer stopped early"
  (known; BUILD.md step 7's remaining scope).
- Client disconnect leaves `generate()` suspended — known, documented at `chat.py:554`,
  deferred; findings 6 and 7 both make it worse than it looked.

### Fixed this round — 16, 17, 22

Scoped by the PM to these three plus the outstanding BUILD.md boxes, on the
constraint that nothing may assume a second Railway instance.

**16 — transient provider errors blamed on the user's file.** A `TRANSIENT_ERRORS`
tuple (`TooManyRequestsError`, `InternalServerError`, `ServiceUnavailableError`,
`GatewayTimeoutError`, `httpx.TransportError`) now covers the whole family
instead of the rate limit alone. Used twice: the embedding loop `break`s on any
of them, so the step returns normally and the browser's existing no-progress
wait retries it with nobody watching; and the generic handler returns **503
without marking the row `failed`**, so the download and the writes — which sit
outside that loop — keep their resume point too. The old advice ("re-upload it")
was not merely unhelpful, it discarded the resume point and re-paid for every
chunk already embedded.

**17 — every chart in a slide deck silently deleted.** Root cause was that
position alone cannot tell a logo from a chart: both repeat in the same spot on
many pages. The filter now renders up to `REPEAT_SAMPLE_PAGES` (3) copies and
drops the group only if they are the *same picture*. Measured against the
pre-fix code on a 6-slide deck: **before 0 charts kept, after 6**, with the
3-page logo case still filtered to 0 by both. The caller also finally passes an
`on_reject`, counted into one summary log line rather than one line per box —
`_items` re-parses the whole document every step, so per-box logging would
repeat itself for every slice.

**22 — partial feedback success reported as total failure.** `record_feedback`
returns the list of parts that did *not* land instead of a bool, and gives the
score and the comment a `try` each. **Not reachable from our own UI**, which
posts the thumb and the note as two separate requests by design
(`chat-view.tsx:198-201`); it needs a direct API call, since the endpoint
accepts both in one body. Fixed anyway because the old contract made the
endpoint tell a caller nothing was saved while the rating was already filed,
and doing as told counted that rating twice — the exact double-count the
two-key split exists to prevent.

Each has a runnable check: `python -m app.routers.documents` (the transient
classification, in both directions), `python -m app.services.ingestion` (the
deck survives, the logo does not), `python -m app.services.tracing` (the
feedback split, including that a thumbs-down is `score == 0` and falsy).
